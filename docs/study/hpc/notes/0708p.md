# 07-08 下午 HPC 中的计算机系统 II

集群把计算节点、网络、存储和调度器连成一个整体。程序申请多少资源、启动多少 rank 和线程、数据放在哪里、怎样读写文件，都会影响运行结果。HPL（High Performance Linpack，高性能 Linpack 基准）、MPI（Message Passing Interface，消息传递接口）、GPU 程序和并行文件系统需要放在同一套资源管理规则中理解。



!!! quote "SchedMD 对 Slurm 的概括（译）"

    Slurm 是开源的集群管理和作业调度系统。它负责为作业分配节点，启动和监控任务，并记录资源使用情况。用户提交的是资源请求和运行命令；调度器决定任务何时获得资源。[^slurm-overview]

## 一次作业如何经过集群

=== "1. 登录与提交"

    用户在登录节点编辑代码、加载模块、编译程序并提交脚本。登录节点不承担长时间的数值计算。

=== "2. 资源分配"

    Slurm 根据脚本中的节点数、task 数、每 task CPU 数、GPU、内存和时间限制，选择合适的计算节点。task 是调度器启动的一份工作，MPI 程序中通常对应一个 rank，即一个独立进程。队列状态反映的是资源和策略，而不是程序是否正确。

=== "3. 启动并行任务"

    `srun` 或集群指定的 launcher 在分配到的节点上启动 MPI rank。每个 rank 内还可以启动 OpenMP 线程；rank 数、线程数和申请资源必须一致。

=== "4. 读取、计算和写回"

    程序从共享文件系统或节点本地盘读取数据，进行计算和通信，再写入日志、检查点和结果。I/O 的文件数量、访问模式和并发数会影响总时间。

## HPC 系统与工作负载

HPC 系统将大量计算节点、互连网络、共享存储和作业调度器组合起来。用户通常登录到前端节点，准备软件环境和作业脚本；调度器为作业分配计算节点；程序在分配到的节点上运行并访问共享或本地存储。登录节点用于轻量交互，不应作为长时间计算场所。[^slurm-overview]

| 部件 | 用户通常做什么 | 需要避免的操作 |
| --- | --- | --- |
| 登录节点 | 编辑、编译、提交、查看日志 | 长时间占满 CPU、内存或 GPU |
| 计算节点 | 运行 Slurm 分配的任务 | 绕过调度器长期登录计算 |
| 共享文件系统 | 存放源码、输入、结果和检查点 | 无节制创建大量小文件 |
| 高速互连 | 传输 MPI/NCCL 数据 | 将管理网络速度当作通信性能 |

![图中对比两种集群组织。左侧 HPC 将计算节点、高速互连和独立存储节点组合；右侧 MapReduce/Hadoop 更强调计算与分布式文件系统共同部署。](assets/0708p/hpc-distributed-cluster.jpg)

*图中比较 HPC 与 MapReduce 的典型组织方式。登录节点、调度器和完整作业路径见后面的 NFS、MPI 与 Slurm 小节。[^slurm-overview]*

资源形状描述程序需要怎样的节点、rank、线程和设备组合。单进程 CPU 程序主要需要一个核心与内存；OpenMP 程序需要一个节点内的一组核心；MPI 程序还需要 rank 间通信；GPU 程序还要申请设备和安排主机到设备的数据传输。

!!! tip "把资源写成一个乘法式"

    例如，`2 个节点 × 每节点 4 个 MPI rank × 每 rank 8 个 OpenMP 线程` 表示总共 8 个 rank、每节点 32 个 CPU。这个表达应能直接对应到 Slurm 参数、`srun` 或 `mpirun` 参数，以及 `OMP_NUM_THREADS`。

## 峰值性能与基准测试

峰值 FLOPS（Floating-Point Operations Per Second，每秒浮点运算次数）根据核心数量、频率、向量宽度和每周期浮点操作估算。它用于说明硬件计算规模，但真实程序还会受到指令组合、数据供给、同步、通信和 I/O 的限制。报告峰值利用率时，应同时说明算子、精度、输入规模和计时范围。[^hpl]

基准测试也有适用范围。HPL 测试高密度线性代数，主要体现浮点计算、BLAS 和网络协作能力；它不能代表随机访问、稀疏矩阵、小文件 I/O 或深度学习端到端吞吐。选择 benchmark 时，应让访问模式接近要解释的程序现象。

```text
时间 = 计算时间 + 等待数据时间 + 同步/通信时间 + I/O 时间 + 其他开销
```

## 计算、内存、网络与 I/O 瓶颈

性能分析需要区分带宽和延迟。带宽描述单位时间可以传输多少字节，延迟描述一次操作最早多久完成。大数组的连续流式访问常受带宽限制；指针追逐、小消息通信和大量元数据操作常更受延迟影响。优化手段要与瓶颈匹配。[^nersc-roofline]

算术强度是浮点操作数除以从主存传输的字节数。Roofline 模型给出可达到性能的近似上界。

$$
P \leq \min(P_{peak}, I \times B_{memory})
$$

其中 $I$ 是算术强度，$B_{memory}$ 是可用内存带宽。这个模型不直接给出优化方案，但能帮助判断一个循环更接近计算上限还是数据搬运上限。

### 延迟与带宽

MPI 消息时间常可粗略写成 $T=\alpha+n\beta$。其中 $\alpha$ 表示启动延迟，$n$ 是字节数，$\beta$ 是每字节传输时间。小消息数量很多时，应关注消息合并与同步次数；大消息传输慢时，应关注布局、带宽和通信与计算的重叠。真实网络还受拓扑、拥塞、协议和集体通信算法影响。[^mpi-standard]

!!! note "区分计算、通信和 I/O"

    一个程序在 16 个 rank 上变慢，可能来自负载不均、等待 barrier、远端 NUMA 访问、网络拥塞或共享文件系统。先在时间线上或 profile 中分开计算、通信和 I/O，再提出优化假设。

## 作业调度与资源形状

Slurm 将节点和可消耗资源组织成分区与作业。`sbatch` 提交批处理脚本，`salloc` 申请交互式分配，`srun` 在当前分配中启动任务。作业先进入队列，资源满足后才运行；排队时间取决于分区策略、优先级、资源请求和集群负载。[^slurm-sbatch]

![SchedMD 的官方架构图展示用户命令、控制端 `slurmctld` 和计算节点 `slurmd` 的关系。记账数据库与 `slurmdbd` 属于可选组件。](assets/0708p/slurm-official-architecture.png)

*图中 `sbatch` 向控制端提交作业请求，`srun` 在分配资源后与节点守护进程协作启动 job step。数据库和备用控制器是否存在取决于集群部署。[^slurm-overview]*

```bash
#!/usr/bin/env bash
#SBATCH --job-name=matmul
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=4
#SBATCH --cpus-per-task=8
#SBATCH --time=00:10:00
#SBATCH --output=logs/%x-%j.out
#SBATCH --error=logs/%x-%j.err

module purge
module load gcc openmpi
export OMP_NUM_THREADS="$SLURM_CPUS_PER_TASK"
srun ./solver input.dat
```

`--ntasks` 通常对应 MPI rank 数，`--cpus-per-task` 通常对应一个 rank 可使用的 CPU 核数。OpenMP 与 MPI 混合并行时，`OMP_NUM_THREADS` 应与后者匹配。使用 `squeue -j 作业号` 查看排队或运行状态，使用 `sacct -j 作业号 --format=JobID,State,Elapsed,AllocCPUS,MaxRSS` 查看完成后的账务信息。[^slurm-sacct]

![SchedMD 的官方实体图区分 partition、job、job step 和 `slurmd`。一个 job 可包含一个或多个 job step，step 中的任务由分配到的节点守护进程启动。](assets/0708p/slurm-official-entities.png)

*图中 `sbatch` 创建 job，脚本中的一次或多次 `srun` 可创建 job step。这一层次解释了同一 allocation 内为何可启动多个步骤，也解释了资源参数和启动参数为何必须一致。[^slurm-overview]*

!!! warning "资源申请和启动命令必须一致"

    已申请 8 个 task，却用没有 Slurm 集成的启动方式只启动一个 rank，调度器仍会保留全部资源。相反，启动的线程数超过申请数，会与同节点其他作业争用 CPU。先用 `srun hostname`、`srun -n N printenv` 等小命令验证分配，再运行实际程序。

### 作业脚本的三部分

批处理脚本同时描述资源、运行环境和启动方式。`#SBATCH` 行由调度器在提交时解析。`module load`、环境变量和目录切换在分配到节点后由 shell 执行。`srun` 在当前 allocation 中启动任务。将 MPI 启动命令放在 `srun` 后，调度器才能把任务数、CPU 集和节点列表传给运行时。[^slurm-srun]

```bash
#!/usr/bin/env bash
#SBATCH --job-name=hybrid
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=4
#SBATCH --cpus-per-task=8
#SBATCH --time=00:15:00
#SBATCH --output=logs/%x-%j.out
#SBATCH --error=logs/%x-%j.err

set -euo pipefail
module purge
module load gcc openmpi
export OMP_NUM_THREADS="$SLURM_CPUS_PER_TASK"
export OMP_PROC_BIND=close
srun --cpu-bind=cores ./solver --input input.dat
```

脚本中的 `%j` 是作业 ID。先把同一脚本中的 `srun hostname`、`srun -n "$SLURM_NTASKS" printenv` 跑通，再启动大型 MPI 程序。这样可以验证节点数、rank 数、每 rank 的 CPU 数和环境变量是否与预期一致。

### 查看作业状态

`PD` 表示作业尚在等待，原因可能是资源、优先级、时间限制或账户策略；`R` 表示正在运行；`COMPLETED` 只表示调度器看到进程成功结束，并不证明数值正确。查看 `squeue -j JOBID -o "%.18i %.9T %.30R"` 了解当前状态和等待原因，使用 `sacct -j JOBID --format=JobID,State,Elapsed,AllocCPUS,MaxRSS,ExitCode` 记录完成后的资源和退出码。[^slurm-sacct]

## 超算的软件栈

从下到上可分为硬件与驱动、操作系统、编译器和数学库、通信库、运行时、作业调度器和用户应用。模块系统负责在用户环境中选择兼容的一组编译器、MPI 和库。MPI 库通常与编译器和网络驱动有关，混用不同模块构建与运行同一可执行文件容易产生难以解释的错误。[^lmod]

```bash
module purge
module load gcc/13 openmpi/5
which mpicc
mpicc --showme:command
```

在实验报告中记录 `module list`、`mpicc --version`、Git 提交和构建命令。性能数字离开这些信息没有可比性。

## 存储系统中的文件位置

并行文件系统把数据分布在多个服务端，使许多客户端能同时读写大文件。它的优势来自并发与条带化，代价是元数据操作、网络路径和共享负载都会影响结果。文件“可以打开”只说明路径解析和权限检查成功，不能说明后续读写具有高带宽。[^lustre]

![并行 I/O 的路径包含应用、MPI-IO 或文件系统客户端、网络、元数据服务与数据服务。一次读写的瓶颈可能出现在其中任一层。](assets/0708p/parallel-io-stack.jpg)

*并行文件系统的访问路径需要结合文件大小、条带、访问模式与元数据操作观察。[^lustre]*

大量小文件会制造大量 `open`、目录查找、创建和关闭操作，常先压满元数据服务。对大规模数据，优先使用较少的大文件、批量读取、顺序访问和与程序访问模式相符的分块。不同系统的条带设置和 scratch 政策不同，应参考所在集群文档再调整。

### 访问模式、条带与元数据

并行文件系统通常把一个大文件分布在多个存储目标上。顺序的大区段读取能让多个服务端共同提供带宽；大量 rank 同时创建或打开小文件时，路径查找、目录项、权限和 inode 等元数据操作可能先成为瓶颈。文件总字节数很小并不意味着 I/O 负担小。[^lustre]

把“每个样本一个文件”的数据集改为分片文件、容器格式或批量读取前，应先确认读取端是否仍能并行、失败后如何恢复、课程工具是否支持该格式。I/O 优化和算法优化一样需要保存访问模式、并发数、文件数量、条带设置和端到端时间。

### 检查点策略

检查点保存足以恢复计算的状态。它应包含模型或数值状态、迭代步、随机数状态、输入版本和必要元数据。安全写法通常先写临时路径，完成、校验后再原子改名；恢复程序只读取带有完成标记的检查点。检查点频率要在写入代价与失败后重算代价之间平衡。[^checkpoint]

```text
checkpoint.tmp/  →  写完分块与元数据  →  校验  →  原子发布 checkpoint-0042/
```

计时 I/O 时，应说明是否包含同步落盘、是否使用 page cache、是否包含所有 rank 的等待时间。否则“写入很快”可能只是把工作推迟给内核或存储系统。

## 指令集、编译器与微架构

ISA 规定软件可见的指令、寄存器和内存语义；微架构决定这些指令实际如何调度、缓存和执行。编译器的 `-march`、`-mtune` 或架构模块会影响生成的向量指令。为某台登录机编译的二进制未必能在较旧计算节点上执行，部署前应确认节点 CPU 特性。[^gcc-opt]

优化选项需要分层验证。先在有调试信息的正确版本上定位热点，再建立 Release 版本，最后对比结果误差和时间。浮点程序中的激进数学重排可能改变舍入顺序，是否允许取决于算法精度要求。

## 内存层级与虚拟内存

CPU 先从缓存读取，缓存未命中后才访问 DRAM；NUMA 节点之间的内存访问又有差别。一次大规模 `malloc` 不一定立即分配所有物理页，首次访问通常决定页面实际放置。多线程数组程序应让线程初始化自己将处理的分块，避免所有页面被一个核心集中触碰。[^linux-numa]

### Cache 地址映射

缓存按行装入，地址的不同部分用于选择集合和比较标签。程序员不必手工计算每一次映射，但需要注意两种现象。连续访问有利于缓存行利用和硬件预取。周期性访问可能让少量缓存集合反复冲突。分块、改变 leading dimension 或调整数据布局有时能缓解冲突，效果需要实测。

### 内存分配与数据位置

给数组选择布局时，先画出最内层循环访问的地址。C/C++ 的二维数组通常按行主序，最后一个下标连续；Fortran 常按列主序。让内层循环沿连续维度走，通常比微调单条算术指令更重要。

```c
/* C 行主序：j 连续，适合放在内层。 */
for (int i = 0; i < m; ++i)
  for (int j = 0; j < n; ++j)
    sum += a[i][j];
```

## 多核、线程和同步

共享内存并行需要确定数据所有权。读多写少的数组可以共享读取；输出数组通常按线程块划分；归约值先放在线程私有变量中，最后合并。并行循环的粒度过细会把时间花在线程调度和同步上，粒度过粗又可能造成负载不均。[^openmp-spec]

不要把 `critical` 放进每次迭代都执行的热循环。先思考能否改变数据分解，使每个线程独占输出区域；若必须累加，优先使用 reduction 或分级归约。

## 性能分析流程

1. 明确正确性判据和代表性输入。
2. 固定工具链、资源形状、线程绑定和重复次数。
3. 测量端到端时间，确认热点占比。
4. 用 CPU/GPU profiler 或硬件计数器解释热点受什么限制。
5. 一次只改变一个因素，重新验证正确性和统计量。
6. 保存可复现命令、原始日志和改动前后的对照。

!!! question "作业脚本自测"

    一个 MPI+OpenMP 程序想在两个节点上运行，每节点 4 个 rank，每 rank 8 线程。请写出资源总量，并说明 `--ntasks-per-node`、`--cpus-per-task` 和 `OMP_NUM_THREADS` 分别应是什么。

    ??? tip "详细答案"

        每个节点有 $4\times8=32$ 个 CPU 线程配额，两个节点共有 8 个 MPI rank 和 64 个 CPU 线程配额。脚本可以写为。

        ```bash
        #SBATCH --nodes=2
        #SBATCH --ntasks-per-node=4
        #SBATCH --cpus-per-task=8
        export OMP_NUM_THREADS="$SLURM_CPUS_PER_TASK"
        srun --cpu-bind=cores ./hybrid_solver
        ```

        `--ntasks-per-node=4` 对应每节点 4 个 MPI rank。`--cpus-per-task=8` 为每个 rank 预留 8 个 CPU。`OMP_NUM_THREADS=8` 让每个 rank 内启动 8 个 OpenMP 线程。还需要确认分区中的节点确实有足够 CPU，并在实际运行时检查没有额外线程造成过度订阅。
